## Selection and evidence

This is an **editorial priority list**, selected for operational impact, coverage across the infrastructure stack, and reviewable current primary-source activity. It is not a measured popularity chart, an adoption survey or a universal severity ranking. Current official repository snapshots establish active engineering work; they do not establish market share or universal performance. Older papers and agency forecasts retain their publication dates.

Every topic has an explanation of its bottleneck, the data or energy that moves, possible responses, their costs, appropriate performance metrics, an operator question, a concrete experiment and claim-level source notes. **Selection & evidence** opens the complete source record in an accessible native dialog. Calculations appear alongside assumptions, formulas and excluded costs. No GPU benchmark or vendor production deployment is inferred from the geometry.

## Quantitative assumptions

Network bandwidth is decimal Gb/s; storage uses binary KiB/MiB/GiB unless stated otherwise. All values below are educational assumptions and analytical bounds, not measured throughput or latency.

1. **Power:** GPU IT floor = `GPU count × assumed watts / 1e6` MW. GPU-only facility floor = `IT × PUE`. The ideal active fraction is `min(1, available facility MW / facility floor, available GPU heat removal / IT floor)`. Defaults are 100,000 GPUs at 1,000 W, PUE 1.20, 100 MW facility budget and 110 MW GPU heat-removal budget: 120 MW requested facility floor, 83,333 ideally capped GPUs. An assumed PUE reduction of 0.10 changes that floor to 110 MW and the cap to 90,909; GPU IT heat remains 100 MW. CPU/NIC/storage and other IT load are excluded, so facility demand is a **lower bound**. Lower PUE is not credited as less GPU heat.
2. **KV:** dense-GQA shape = 80 layers, 8 KV heads, head dimension 128. BF16 K+V bytes per retained position across the whole model group = `2 × 80 × 8 × 128 × 2 = 327,680`. At 8,192 reserved positions and 64 sequences, the payload is 160 GiB; assumed 8-bit payload is 80 GiB. An 80-GiB KV-only budget gives ideal caps of 32 versus 64 sequences. Scale metadata, weights, allocator padding and workspace are additional. Quantization quality and actual fit are not predicted.
3. **P/D fabric:** same BF16 GQA shape. One 8,192-position prompt is 2.5 GiB of KV. Four simultaneous handoffs total 10 GiB at one shared endpoint. Wire floor = `total bytes / (Gb/s × 1e9 / 8 × 0.70)`. A hypothetical 2× endpoint halves that floor without deleting state. Runtime, remote contention, redistribution and coordination are additional; it is not the full handoff latency.
4. **MoE:** 16 experts, **distinct top-2** choices, hidden width 8,192, BF16. Logical assignments = `tokens × 2`; logical one-way payload = `assignments × 8192 × 2`. A fraction of **tokens** chooses the hot expert once, so it can never receive more than the token count. Remaining assignments are uniform over the other 15 experts. Baseline peak visits = `ceil(max(hot, remaining/15))`; candidate peak = `ceil(max(hot/2, remaining/15))`. The replica preserves logical routing but needs additional state and correct dispatch. Default payload remains 32 MiB, with peak expected physical-worker visits 820 → 410. These are neither latency nor physical all-to-all wire bytes.
5. **Reasoning:** fixed 500-ms TTFT plus `output length × expected decode cost`. Baseline target step defaults to 25 ms. Candidate cycles draft four proposals at an assumed 1 ms each and verify at the selected target-step cost. With independent conditional acceptance `p`, expected advance = `1 + p + p² + p³ + p⁴`; cost per expected token = `(4 + targetStepMs) / advance`. At zero acceptance, 29 ms loses to the 25-ms baseline. Real verification cost, batching, queueing, compatibility and quality are outside the toy.
6. **Precision:** generic BF16 weights use `parameters × 2` bytes. Candidate storage = `parameters × bits/8 + ceil(parameters/block) × 4`, declaring one FP32 scale per block. Default 70B parameters, 4 bits, block32 gives 35 GB payload plus 8.75 GB scales. This **does not reproduce NVFP4**: the cited recipe has hierarchical scaling, E2M1 values and different 1D/2D block choices. No throughput, accuracy or training-stability result is predicted.
7. **RL:** completions = `prompts × group`; new rollout positions = `completions × fixed output length`. Defaults 16 prompts, G=8, length1,024 produce 128 completions and 131,072 new positions. Full BF16 70B publication to four destinations is 560 GB of **logical delivered payload**. The conditional adapter example has 41,943,040 BF16 parameters (`80 layers × Q/O × rank16 × (8192+8192)`), giving 320 MiB across four destinations. It requires a compatible resident base and runtime. It does not eliminate rollout, reward/verifier, activations or learner work; logical publication bytes are not collective wire volume or synchronization time.
8. **Placement:** homogeneous eight-GPU nodes with 2/4/8-GPU node-local gangs. Baseline groups = `nodes × floor(free per node / gang)`. Candidate packs the same total free slots into whole nodes and counts complete gangs. Defaults four nodes with four free slots each cannot place an eight-GPU local gang; ideal compaction admits two groups while retaining exactly 16 free slots. It assumes movable workloads and excludes migration/restart cost. It is not an automatic Kueue compaction guarantee.
9. **Recovery:** first-order expected waste = `C/T + (T/2 + R)/M`, with blocking save cost C, interval T, restore cost R, and **whole-job** MTBF M. The equation's optimum is `sqrt(2CM)`. Defaults C=30s, T=300s, R=120s, M=12h give 10.625% approximate waste. The derived interval is about 26.83 min with about 4.00% waste, but expected rework per failure rises from 2.5 to 13.42 min. Independent uniform failures and small overhead are assumed. Durability, correlated faults and actual asynchronous checkpoint behavior are outside the model.
10. **Isolation:** each tenant needs a declared block count; a common-prefix fraction is an expected block-equivalent aggregate. Unsafe global reuse = `common + tenants × private`; tenant-scoped storage = `tenants × blocks`. Defaults eight tenants, sixteen blocks each and 50% overlap produce 72 versus 128 block equivalents. No breach probability, timing experiment or security proof is implied. **The server must authenticate and enforce the scope; client-chosen salts alone are not authorization.** Within-tenant reuse remains possible.

The IEA's 415 TWh (2024 estimate) and approximately 945 TWh (2030 Base Case projection) describe **all data centres**, not AI-only consumption. The latter is a forecast from the dated report, not a measured 2030 result.

## Interaction and implementation

**Top 10 / The issue / Experiment / Evidence** separate discovery, explanation, intervention and source reading. The ten-topic dock, clickable 3D station labels and topic selector all change the same state. **1–9, 0** selects a topic; arrows move between topics; **Space** controls the tour; **F** focuses the selected station. Manual topic selection and the tour frame the selected station; opening Experiment brings its geometry into view alongside the controls. **World/Details** clears/restores the reader. Cinema retains the correct lesson controls. The tour uses five seconds of teaching time per topic and wraps after ten; automatic changes preserve playback, while manual choices and experiment edits stop it.

Sharing saves the selected issue, panel, intervention and bounded controls in a project-path-safe URL. Reload opens it paused. Incompatible model/lifecycle query parameters are cleared. Leaving restores the retained base infrastructure clock and the same renderer. The main header offers horizontal navigation scrolling at narrow widths; the ten-topic dock becomes two rows on phones. Reduced motion disables automatic playback; the no-WebGL path retains all ten topics, experiments, sources and an interval-driven tour where motion is permitted.

`src/issues/catalog.ts` owns the researched content, source scopes, control bounds and visual legends. `model.ts` contains pure calculations and URL parsing. `HotIssues.tsx` renders the spatial HUD, study surface and methodology reader. `src/scene/examples.ts` adds ten radial stations using distinct instanced roles, local signal routes and bounded state updates. It shares the existing effects quality controls, picking, camera and GPU-resource disposal.

Unit coverage checks mathematical conservation, independent constraints, counterexamples, URL round trips, bounds, source integrity and actual instanced geometry changes. Browser coverage exercises all ten stations, persistent-canvas transitions, live experiments, research readers, sharing/reload, keyboard/tour/cinema, narrow layouts, reduced motion and WebGL fallback. The existing game, model and lifecycle suites remain regression checks.
